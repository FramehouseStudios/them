# PostgreSQL custody-request fence candidate

This is an unshipped, additive backend candidate. It does not certify that an earlier save never happened: it certifies that the exact request identity is blocked from future delivery. The writer's local copies must remain held and any replacement requires a fresh request ID and a freshly checked server head. A saved original receives a separate full-hash `already_saved` response; partial legacy matches fail closed.

The authenticated route `POST /screenplay/projects/:projectId/version/fence` accepts the original request fields and a lowercase 64-hex `local_request_digest`. A successful blocked response contains `stage: screenplay_version_fence`, `status: future_delivery_blocked`, `proof: pg_request_fence_v1`, project and request IDs, the echoed local digest, server request hash and `head_version_id_at_fence`. The head is historical, not authority for a later save. The local digest is client correlation, not authentication. The database ledger stores no draft, title or notes.

Migration 015 installs a permanent ledger and `ENABLE ALWAYS` guard. The block function locks and updates the owner row in the same transaction as fence insertion; failed attestation or invalid state produces no proof. The guard rejects later owner payloads carrying the fenced request ID, including the legacy `allow` strategy. It permits identical historical ID-less versions in a fenced project but rejects new or altered ID-less versions there; unrelated projects are not subject to this restriction. The guard rejects all non-READ-COMMITTED writes to the owner table, including unfenced owners, because stale stronger-isolation snapshots can miss a ledger insertion after owner deletion/recreation. This is a material compatibility constraint, not yet approved for deployment. The short-film beta's ID-less writer has not been migrated or proven compatible with a fenced project.

## Required operational controls before any deployment

- Production remains held. Apply migrations only as a separately controlled schema owner; the runtime login must not own or inherit ownership of the owner table, fence ledger or either function, hold `TRIGGER`/ledger mutation privileges, create objects in `public`, be superuser, or switch roles. Grant runtime `EXECUTE` only on `public.screenplay_block_request(text,text,text,text,text)` after normal application table grants. The route fails closed when the required role or schema checks do not pass.
- Preserve the ledger and trigger across account deletion, restore and rollback. The guard permits the existing content-free owner-deletion tombstone while retaining the ledger. This retains owner/project/request-derived identifiers and hashes beyond account deletion; privacy and retention authority is unresolved. Do not claim complete erasure or deploy until the human-owned policy explicitly covers it.
- Once any proof has been issued, do not remove the ledger or guard as a rollback: that would invalidate previously issued proofs. Disable client use of the route while retaining database enforcement; migration and privileged restore procedures need a separately verified forward-only operational plan.
- Fence transactions force `synchronous_commit=on` through transaction commit even when the runtime session default is `off`. This waits for local primary WAL flush under normal PostgreSQL durability settings. It does not guarantee a standby has the fence: failover durability requires an appropriately configured synchronous standby and independently verified backup/restore procedures. The proof is sent only after the autocommit database query returns; callers must not expose it before an enclosing transaction commits.
- Administrative or migration-owner tampering, untrusted security-definer functions, schema restores, missing request identity in older worker versions, and loss of PostgreSQL durability are not ruled out by these local checks. Verify deployed roles, trigger/function integrity, supported worker fleet, backups and account-purge behavior before considering a rollout. JSON persistence never issues a fence proof.

## Local evidence and gaps

On the isolated task-owned PostgreSQL 16 instance, the Node 20.20.2 authenticated endpoint checks passed 3/3, 0 skips: blocked old `allow` retry, fresh-ID save, already-saved receipt, nonowner ledger-delete refusal, unsafe superuser refusal, disabled trigger and temp-catalog spoof failure, corrupted owner identity rejection and recovery after database repair, queued legacy upsert, owner tombstone/recreation, non-READ-COMMITTED rejection and JSON no-proof. Logs: `/private/tmp/them-t1368-node20.log`. Earlier synthetic prototypes exposed a repeatable-read bypass and snake-case ID bypass; the candidate was adjusted and their original red observations must not be described as passing production proof.

The client and backend have not yet been combined into a real UI scenario. Full backend/iOS gates, physical iPhone, the actual shipping backend, original PR integration and production privileges are unverified. A pre-existing cache mismatch can otherwise retarget a refresh; the candidate evicts mismatched cached/normalized owners without writing either account and the local corrupted-row test checks recovery after repair. Broader owner-write paths, absence of untrusted privileged database functions, source-history compatibility and the precise supported legacy fleet need review before use.
