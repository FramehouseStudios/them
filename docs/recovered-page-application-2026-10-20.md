# Recovered page application — T-1038

## Connected behavior

Recovered full-page replies now offer **Review placement in Studio**. The
existing Studio action queue owns navigation. A request waiting at first mount
is handled after canonical project hydration, rather than validated against an
empty/unloaded editor. The preview is a child presentation controller, not new
product state on either god view.

For an existing project, the proposal requires the original project, revision,
exact UTF-8 draft identity and supported original placement. Insert-after uses
the original logical line, not today's cursor. New rewrite requests additionally
retain their exact validated original UTF-16 selection and text identity locally;
older ambiguous selections stay read/share-only. These local fields do not enter
the backend/provider request serialization. Native insertion and recovery share
the same heading de-duplication and paragraph-padding owner.

Explicit confirmation first atomically retains an immutable placement decision
in the existing recovered receipt. It then enters Studio's canonical dispatcher
with a stable save ID. Only after the existing durable save queue admits it can
the editor adopt the proposal. The canonical handler verifies owner/auth,
project/base and original-or-already-proposed exact bytes; newer words cause a
parked save, never a fallback cursor insertion or automatic overwrite. Ordinary
saves retain their prior path. Receipt acknowledgement requires the canonical
saved-draft identity and a nonempty server version. A recovered response is not
treated as a screenplay save acknowledgement.

Reopening a prepared/saved receipt checks its immutable decision and canonical
loaded saved state, preventing a second insertion after lost acknowledgement or
relaunch. The original response, request and context remain retained. Deleting
a recovery copy is not an undo of an already explicitly requested screenplay save.
