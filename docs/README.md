# io.them Documentation Guide

The repository keeps product direction, accepted decisions, implementation
contracts, and release evidence separate so proposals do not silently become
shipping claims.

## Authority order

1. [`AGENTS.md`](../AGENTS.md) - current project execution and engineering rules.
2. [`DECISIONS.md`](../DECISIONS.md) - product-lead accepted decisions.
3. Current code, tests, API schemas, and release proof.
4. Product and architecture proposals in this directory.
5. Historical task, coordination, and archived proof material.

## Start here

| Need | Document |
| --- | --- |
| Product vision, customer, boundaries, and phases | [`product/founder-product-brief.md`](product/founder-product-brief.md) |
| Platform scope and engineering/product gate | [`product/platform-proposal.md`](product/platform-proposal.md) |
| Technical boundaries and complexity triggers | [`architecture/technical-blueprint.md`](architecture/technical-blueprint.md) |
| Operative V1 checklist | [`v1-definition.md`](v1-definition.md) |
| API response contracts | [`schemas/INDEX.md`](schemas/INDEX.md) |
| Current release clearance | [`v1-release-preflight-proof.md`](v1-release-preflight-proof.md) |
| Backend deployment | [`../backend/DEPLOY.md`](../backend/DEPLOY.md) |

Product/architecture references use evidence labels and explicit proposal
banners. If a proposal materially changes pricing, privacy, ownership,
retention, training, platforms, or collaboration, record a proposed decision
and obtain product-lead acceptance before implementing it as policy.
